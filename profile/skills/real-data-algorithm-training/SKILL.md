# 真实数据上的算法训练任务

为课堂、实训基地或招聘考核设计「最简单的算法训练 / 实际案例」时用。核心：**不造数据集**——从公司已有的真实交付物里找，标签从客观事实里倒查出来。

## 触发条件

- 用户说「找一个实际案例做算法训练 / 最简单的分类算法 / 有没有合适的数据和问题」
- 为数据工程课、实训基地、招聘考核设计算法练习或考核题

## 判据：什么算「合适」

五条同时成立：**真实**（出自公司交付物或业务系统——产教融合的要求是「教育用真实业务当教材」，玩具数据不合格）、**金标白拿**（标签能从客观事实倒查：事件本身 / 路径位置 / 既有字段，不需要人工标注）、**画像清楚**（先算行数·实体数·时间跨度·缺失率·标签分布）、**一步能跑**（pandas 读表 + sklearn 基线，几十行、单机分钟级）、**教学点自足**（数据本身要能踩到该教的坑）。

**三条准入筛（2026-10-01 实证，任一不过直接淘汰候选，不要留到「再看看」）**：

- **标签是事实，不是观测结果。** 「这篇文档该放哪一层」有标准答案，可以逐条核对，判据还写在文档规范里、人能讲清；「这个 PR 会不会被合并」只有统计相关性，没有人能指着某一条说「标准答案是 X」，做出来也无从验证。**预测「会不会发生」的任务默认出局**——这是用户否掉第一个提案的原话（「这个算法结果没有办法直接验证」）。
- **有信号。** 先用同一个简单模型试跑，**低于「全猜多数类」基线的候选当场淘汰**。实证：四类记忆分类 0.265 < 基线 0.302——标签是作者的写作意图，文本里根本没有信号，这类任务再简单也做不成。
- **形状可用。** 类别互斥、样本够（百级以上）、不严重失衡。严重失衡的（实证：某仓提交类型 chore 占 78.5%，全是子模块指针提交）当「不平衡」专题可以，当第一课会教出坏直觉。

## 步骤

1. **先盘「自己天天在手工做的判断」，再找数据——候选入口是任务，不是数据集。** 这是用户 2026-10-01 亲自定下的判据（已落档 `quanttide-algorithm/data/insight/candidate-selection.md`）：盘一遍谁每天在手工做哪个判断，那里就是候选。理由三条——需求已经发生（不用推演）、标注是当事人每天顺手产出的（不用专门标）、做出来省的是他自己的时间。
   - **反面教训（同一会话）**：从「哪里有待标签的数据」倒着找，做的是**检索题**——用几条技术指标把候选逐个淘汰，剩一个就用它，拿不出任何正向理由说「这个值得做」。用户对第一个例子的真实选择理由就是「我确实天天需要分类，这是一个我天天在手动训练的场景」，数据好看与否不是理由。
   - 数据侧扫描是**兜底**（手上确实没有日常判断可盘时）：`find <repos> \( -name "*.csv" -o -name "*.json" -o -name "*.jsonl" \)` 按文件大小排序；真实数据集几乎总在某个 `profile/`、`delivery/` 或 `fixtures/` 目录下（实证：一份 22.9 MB 的交付数据集就躺在 `domains/quanttide-data/data/profile/` 里，同目录还有交付说明书和采集脚本）
2. **摸画像**（不可省）：`uv run --quiet --with pandas python3 -` 读入 → 行数/实体数/日期跨度 → 各列缺失率 → 候选标签的类别分布。**数字实取，不估算**（估算值会被用户追问）
3. **多标签试跑再定题**——同一份数据往往能切出好几个题目，别只试一个。用同一个简单模型（逻辑回归）跑 2–4 个候选标签，比测试集 AUC 与基线
4. **按难度分档**——选**近平衡**的那个当第一课（基线 ~0.5，模型明显超基线才给得出正反馈）；不平衡的往后排，当「别只看准确率」的教材。**同一份数据能切出台阶**：用标签的粗细层级造三档（实证：同一批文档切 2 类 → 4 类 → 8 类，实测 0.898 / 0.793 / 0.656，基线 0.659 / 0.487 / 0.321），最窄那档给新手第一个正反馈，最宽那档留给考核题的进阶要求
5. **每档都报基线**——「全猜多数类」的准确率。不看基线就不知道模型有没有用
6. **交付形状**：数据位置 + 题目一句话 + 标签定义 + 画像数字 + 分档表（正例率/基线/模型准确率/AUC，**实测值**）+ 四个教学点 + 最小闭环命令

## 坑

- **特征泄漏**：与标签同源的字段必须排除（用 `merged_pr_count` 做标签就不能把它当特征）；「历史」统计一律 `shift()` 之后再算
- **时间切分 ≠ 随机切分**：带日期的数据按时间切（先训后测），随机切会虚高——实测时间漂移能吃掉约 10 个点的 AUC，而这落差本身就是最好的教学素材
- **准确率在极不平衡时骗人**：实测某档正例 3.8% 时模型准确率 0.960 **低于**「全猜多数类」的 0.962
- **给判断不给清单**：用户问「有没有合适的」时要给**判断**（用哪个、为什么、数据在哪），不是罗列所有可能性
- **防主题泄漏：标签不能与主题同构**。实证——「这段内容能不能进公开仓」看着量足（私有侧 1027 篇），但公开/私有是按业务线画的（某条业务线整条 432 篇全在私有侧），模型只会学到「主题 → 可见性」，数字漂亮而没学到东西。这类必须先按主题配对（同一主题的公开版 vs 私有版）再谈分类。
- **确定性检查不该占一个实验位**。能被一次 `ls`/`grep` 验掉的事（引用的文件名/参数是否真的存在）是规则能扛的，药方是检查脚本不是模型——按域意图（「规则引擎不容易处理的问题才孵成算法」）它不属于算法域，要当场说出来并排除。
- **金标太薄的候选当场放弃**。实证「该不该新建文件」全仓只有 10 篇是「建了又删」（`git log --diff-filter=AD`），撑不起一个实验。反过来，**同一批数据可以复用来排难度台阶**：换标签轴就是新题（实证同一批 1210 篇文档切 2 类 / 4 类 / 8 类）。
- **脱敏先确认可见性**：`gh repo view <repo> --json visibility`——只有公开仓的数据集才能进公开教材
- **先跑通再汇报**：给建议前把最小基线真跑一遍，用实测数字说话
- **先问用途**：课堂用 / 招聘考核用 / 自练，口径不同（考核题要卡难度与金标，课堂题要能讲透教学点），落档位置也不同
- **呈现候选不要编号分组**：平铺三五条，每条一句话说清「做什么 / 规则为什么做不了 / 答案怎么对」。**禁用 A1/B2 式编号 + 跨条交叉引用 + 嵌套表格**——用户会直接说「太乱了看不懂」，那之后要做的**是砍到三条以内、改成大白话，不是补解释**
- **反思时不要自我否定式找毛病**：用户让复盘「这个例子是怎么选的」时，别把做对的选择说成「侥幸 / 事后附会 / 幸存者」——那是把自己做对的东西扔了，用户会直接纠正「反思方向错了」。要提的是**可复用的判据**（当时用了哪几条筛子、判据是怎么来的）；判据是踩过一次坑之后总结出来的，这就是它该有的来历
- **评估标准必须挂业务侧**：把任务的成败标准定成「分类准确率」，是**从标签倒推任务留下的胎记**。落档时必须先写业务侧验收标准（本域即「做出来之后人不再手工做它」，来自候选入口那条洞察），再老实说清现有证据只到模型层、业务层还没测——不要拿模型指标冒充业务结论
