## 核心判断写作法（从对话中提炼的实例）

"流程依赖人的根因是流程破碎"——判断句结构：**现象（依赖人）→ 否定浅因（不是判断难/自动化不足）→ 真因（断片间衔接靠人肉）→ 方向隐喻（筑河床）**。用户认可的表达方式：否定多个浅层解释后给出单一根因，配一个可复用的隐喻。

实例链（qtclass-private）：
1. 现象：处理一个申请 6 步、48 处 lark-cli 调用、10 个系统横跨
2. 否定：自动化收效甚微（在断片内自动化，断片间无法自动化）
3. 真因：流程破碎——每段断片用当时最顺手的工具，衔接无定义
4. 方向：筑河床（连续流程），外部系统逐段降级（邮箱→异常通道、Bitable→档案镜像、群→社区场所）

## 演进计划写法（P 系列 + 投入分界）

- P 系列（P0 图纸 → P1 MVP → P2 拆除 → P3 制度化），不用 T 系列（T 像任务清单，P 强调阶段）
- 每阶段带**验收判据**（如"稳定运行两周无人工兜底介入"）与**退出条件**
- **投入分界表**防方向漂移：可平移层（业务流/契约/资产）✅ vs 入口形态层（GUI/CLI 壳）❌——教训：给过渡形态加 GUI 是一次性投入
- 判断标准一句贯穿："每一段还在靠人缝合的衔接，就是下一个要修的缺口"

## 治理与动机类判断的结构（实训基地实例）

集体动机引导（实例：实训基地自治交接后）：
- 分野：个人动力=交换（任务→券），集体动力=共同拥有（我们的东西）
- 行为信号："我配合安排"（等指令）vs "我们决定做 XX"（自发发起）——后者是发芽信号
- 操作原则：改利益流向不做说教；集体给予物=以主体名义、集体署名、交付给真实受益者的成果
- 校验标准："这件事做完，谁的生活因为『XX』变好了？"——答案是主体自己或真实外部对象才对

## Specification 与 Contract（用户定义，2026-09-10）

- **Specification** = 「可接受行为的描述」
- **Contract** = 「交互双方义务与保证的、带责任分配的 specification」
- 所有 contract 都可以看作一种 spec，但不是所有 spec 都是 contract。

用法：写领域规范/契约文档时先问这段文字是行为描述（spec）还是带义务与保证的约定（contract）。案例与验收类段落实质是 contract 条款——**义务写在流程段、保证与责任分配写在验收段**（实证：work 域手册的产物规范「每条内容流动有单一去处」是义务，「未犯常见错误：把 `gallery.md` 改成 `case.md`」是责任约束）。这条定义写在 journal 里即可，别顺手改仓库结构去体现层级。

## 状态机文档模板（流程显性化）

七节结构：状态集（含时限）/迁移表（触发事件/执行者/副作用）/通道合流/字段映射（现状→状态机，关键动作是"剥离"）/硬约束（案例固化为护栏）/实施顺序/显式排除（防膨胀）。

第八节"演进方式"四零件框架：**状态/迁移/触发器/副作用**——未来改流程=零件增删改；判断标准"这个迁移的触发，人在不在环上"（不在环→执行者改系统自动，对账与阻断规则删除）。

## Bitable/lark-cli 契约细节（qtclass 实测）

- `create_records` 元素直接是字段 map，**无 fields 包裹层**
- lark-cli 文件参数（--json @path / --body-file / --inline）**必须相对 cwd**，封装层统一 chdir 仓库根
- 状态机字段剥离：`状态`（流程枚举）与 `评估分组`（结论属性）语义分离
- 邮箱从来信 SMTP 头复制勿手打；applink 仅飞书客户端有效（外部邮箱需二维码 inline）；群二维码 7 天过期
