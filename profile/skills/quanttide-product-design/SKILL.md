# 量潮产品设计纪律

## 目标

为量潮产品做设计（studio 页面/需求地图/roadmap scope）时，遵循用户的产品构建观——每个概念必须能说清、是动作、来自真实需求；规划必须经得起验证。避免"发明抽象层"与"演示层产品"。

## 流程（设计时的五条纪律）

### 1. 用原始概念，不转译

产品方案已有的概念（如 4D 认知过程：感知→理解→预测→决策）**直接作为导航/结构**，不发明派生词（"收集/澄清/结构"是转译，被否）。

- 案例：qtcloud-think studio 导航 = 感知/理解/预测/决策（4D 本身），不是"收集/澄清/沉淀"
- 判断：如果界面概念在领域模型里已有对应，用领域概念

### 2. 任务 = 动作（动词+名词），且匹配活动本质

需求地图/roadmap 的任务名必须是动作："判断清晰度"✅、"清晰度判断"❌；"澄清想法"✅、"澄清对话"❌。

**任务动词必须匹配活动的本质动作**（用户纠正："预测的任务不太对"）：
- 预测活动 = **从现状推未来** → 任务应是推演类（识别模式/推演走向）
- 曾错写"挂接本体/升级模式"（结构组织）——是整理动作不是推演，被否
- 判断：活动叫什么（推演/加工/收集），任务就做什么——任务与活动同性质

### 3. 语义诚实：说不清就砍

每个概念必须能回答"用户具体做什么操作"。被问倒（"对照本体是什么？"）就移除，不悬挂。

- 案例：预测页"对照本体"（推演与本体校验）——说不出操作方式 → 砍
- 案例："升级为情境意识实例"——说不清独立动作 → 简化为"加工完成即形成"（自动，无按钮）

### 4. 需求地图是法源，界面不发明

界面/roadmap scope 不得包含需求地图（profile requirement.md）没有的任务。

- 案例：studio 的"本体树呈现/实例挂接/模式升级"——需求地图移除后，界面同步移除
- 双向同步：改需求地图必须同步 roadmap scope 和 studio 页面功能，反之亦然

### 5. 验证先行：最小闭环 + 真实使用

规划功能前先问"怎么证明值得做"——答案是**用出来的才算数**：

1. **最小闭环先行**：只做高频路径（每天要用的），一周内真实用起来
2. **真实使用检验**：自己用 1-2 周——主动用/缺了难受 = 值得做
3. **砍掉验证**：砍掉不受影响 = 不值得做（对每个功能问"砍了会不会难受"）
4. **数据驱动**：上线后按使用频率砍死功能、深化活功能
5. **延迟高级功能**：没有数据积累的高级功能（如预测页的识别模式/推演走向）就是空壳——等实例数据积累后再判断

### 6. 命名跟惯例（目录/字段/组件，2026-08-23）

用户会逐层纠正命名——**用领域标准与现有仓库一致命名，不发明**：

- **目录分层**：模型放 `models/`，仓储放 `repositories/`（DDD Repository——对齐 qtcloud-agent 惯例）；"data/ 不应该存在"、"那应该叫 models/"、"和 repos/"——不发明 domain/infrastructure 细分（过度分层被否），也不发明 services/ 层（AI 加工访问归入 repositories/）
- **字段惯例**：任务用 title+description（Trello/Jira 标准组合，content 太泛被否）；枚举值用户指定（status：未开始/进行中/评审中/已完成；priority：紧急/高/中/低）
- **组件 vs 页面分层**：页面（screens/，路由级）+ 组件（views/，弹窗等复用单元）——任务详情做成弹窗组件在清单内就地打开（"task-detail 做个组件就可以，然后清单里弹窗点开"），不建独立页面
- 判断：新概念先问"现有仓库/领域标准里叫什么"——有惯例跟惯例，无惯例用最直接的心智词

### 7. doc 文档体系（qtcloud 系列 studio）

设计产出写入 `src/studio/doc/`（对齐 qtcloud-think/qtcloud-execute 模式）：

```
doc/
├── index.md            # 模块设计 + 实施分解（勾选清单）+ 测试原则
├── models/<name>.md    # 领域模型（定义/枚举/流转/序列化/测试/验收）
├── repositories/<name>.md  # 仓储（接口/实现/失败降级/测试）
├── screens/<name>.md   # 页面（功能区 ASCII/交互/数据/测试/验收）
└── views/<name>.md     # 组件（弹窗——组件与页面分层）
```

每文档固定结构：**定位 → 设计 → 数据 → 测试 → 验收**。
配套：ROADMAP.md（做什么）+ TODO.md（实施清单——分"只需单元测试的"与"需组件测试的"两步实施）。

### 8. 领域建模同样适用概念纪律（事件风暴/DDD，2026-08-23）

事件风暴（领域事件/命令/聚合/事件流）写 specification 时，同一把尺子量**聚合与字段**（qtcloud-execute 案例）：

- **聚合最小化**：从核心实体出发（执行云 = Task + TaskList 两个聚合），不为文档结构/流程发明聚合（曾写 JournalEntry/Business/ProfileItem/Distillation 四聚合——被否："聚合应该只需要 Task 和 TaskList 足够了"）
- **字段砍掉验证**：被问"是什么"且答不出独立用途的字段就砍——blockReason 被问 → 阻塞=status 的一种（blocked 态），砍掉独立字段；原因记在 content 里
- **字段补全**：Task 缺 title 被纠正（"缺少 title"）——标题（一句话概括）与内容（描述）分开，不合并
- **清单 = 业务实体 + 组内分组**（2026-08-23 修正："清单是视图"被否）：一个业务一个清单（TaskList 实体），一个职能一个清单内分组（Group）——飞书任务/滴答清单同构，且与 profile 档案结构同构（业务文件夹 × 职能文件）
- **清单动态化**：不静态假设清单集合（用户："不应该对清单做静态假设，而是应该有切换器"）——清单从数据加载（仓储遍历），新增业务=新增清单，切换器自动跟随；不硬编码固定 Tab
- **分组命名**：Group 不叫 Section（用户问"分组为什么是 Section"——受现有代码影响的自创词被否，用与"分组"心智一致的 Group）
- 事件/命令命名随聚合收敛：任务已记录/已分组/已确认/优先级已调整/阻塞已标记（不是"日志已记录/档案已更新"）

### 9. 确认布局后仍要验证产品语义（看板 vs 表格，2026-08-23）

用户确认了布局指令，**不意味着它就是那个产品**——交付前用产品语义再验一次：

- 案例（qtcloud-execute 看板）：用户确认"列=分组、行=状态"——我做成**固定网格矩阵**（行列交叉定位、BoardProjection = 分组×状态 Map）——交付后用户指出"BoardView 只是一个表格，不是真正的看板"。
- 正确语义：**看板的关键是列内流动**——列=分组泳道（职能），行=**列内状态分段**（未开始→进行中→评审中→已完成，列内从上到下推进线），卡片在列内流动；不是行列交叉定位的格子。
- 后来用户自己进一步修正：状态放列（列=状态泳道 + 拖拽跨列推进）——分组降级为筛选器/或 Task.category（业务自定义分类，不枚举约束）。
- **教训**：布局（怎么摆）确认后，仍要问"这个布局的交互语义是什么"——数据形状（矩阵 Map）会悄悄把产品变成表格；从交互（流动/推进）反推数据结构，不是从数据结构推导交互。
- **反思方向**：被指出"不是 X"时，先检查自己是否从"数据结构/技术实现"出发替代了"产品形态"——不是把责任推给布局选择（用户确认过），而是自己没做语义验证。

### 10. "检查/核对"类请求 = 要方案，不是执行令（roadmap/文档更新，2026-08-26）

用户问"查看 X，是否有过时信息需要修改，是否有最新信息需要添加"——**这是要分析报告（过时点+新增点+修改方案），不是授权修改**。直接改并提交推送 = 越权（用户："我还没同意你修改呢"）。

- **流程**：分析 → 给方案（修改点 + 修改理由 + 自查的可疑点）→ 用户拍板 → 才执行
- **"概括核心"** = 让方案更概括（不是让执行更简略）
- **"先核对，你的核心理解是什么"** = 先陈述核心理解与修改理由让用户核对——修改不一定错，但用户不理解就不该发生
- 用户拍板后执行仍要**陈述理解再动手**（如实训基地双路径——我删了"免费上课送实习"因为没核对 journal 8/8 原文"课堂实训服务，附带招聘机会"，实际它是双路径之一的战略表述）

### 11. roadmap 更新验证先行（2026-08-26）

roadmap 过时信息判断**先核对最新事实**（journal/profile/群聊记录），不确定的不删：

- 案例：training-base.md 的"免费上课送实习"被当做过时删掉——实际 journal 8/8 有原文（"课堂实训服务，附带招聘机会"）——是**双路径之一**（课堂→招聘），删错
- 正确做法：可疑表述先搜 journal/profile 确认语义，再判断过时 or 保留
- **roadmap 结构镜像组织**（结构即真实在公司级路线图的应用）：跨领域主题（实训基地=串联课堂/招聘的枢纽）放公司级 `intro/`（公共事实单一来源）；领域目录（qtclass/qtrecurit）只写自己的侧面（同名同构文件 training-base.md，相对链接引用 intro）；领域内 index.md（整体）与专项文件（training-base.md）分离

### 12. 业务域建模：从职能域提取、重组成子领域、直接用业务概念表达（2026-09-24）

用户两次纠正 roadmap 写法后定型的核心思路：

**问题**：职能分解（数据分析/商务/项目管理）是为了内部执行方便——不同职能分别去做。但职能之间有信息重合（如数据处理流程和项目排期），上层拼接时效果很糟。客户需要看到的是**项目的 5 个阶段，每个阶段有某一个角色在做某一块的事情，按明确的顺序进行**。

**解法**：把一整套东西定义为一个「业务域」：
1. **从职能域提取**：数据分析、商务、项目管理——各职能域里跟这个业务相关的部分
2. **重组成一个子领域**：如「量潮数据」——不是职能的拼装，是一个完整的业务概念体系
3. **直接用业务域的概念表达**：客户看到的是业务域的阶段、每阶段谁做什么、按什么顺序——不是「数据处理模块 + 商务模块 + 项目模块」

**具体整合点方法**（用户确认「这个方向对了。列具体的整合点」）：
- **逐阶段整合**：每个阶段列出「谁做什么」+ 哪些职能域内容合并成哪个业务概念（如调研阶段：报价 + 需求分析 → 「需求评估」；蓝图 6 步是谈判阶段给客户看的「方案」，不是「数据域的东西」）
- **横切整合点**：跨阶段要统一的（如三套分解统一为一套、交付物只出现一处、工作档案/宣传册/教程/手册都按业务域组织）

**关键判断**：职能分解是内部的事，客户视角是业务域的事。业务域要有完整的建模思路，不是简单拼装职能域。

**反模式**：「业务域组合职能域现成方案」——这是拼装，被否。正确是业务域自己把业务想清楚，职能域提供内部支撑能力。

### 13. 视角切换：从「顾问」到「客户/CEO」——代笔 vs 主体（2026-09-29 qtconsult）

产品从服务「乙方作业」转向服务「甲方主体」时，别只换界面名——**换的是谁在说话**：

- **本质**：顾问视角里看板是「我的作业」（交付物，**有终点**——结项就关）；客户视角里看板是「我的处境」（生意继续，**没有终点**）。所以顾问的四阶段是**项目生命周期**，客户看到的是**持续的经营循环**。
- **四轴差异**：主体（顾问：客户是分析对象／客户：自己的生意是主体）· 权威（顾问是「方法」的权威／客户是「事实」的权威）· 目的（交付物＋说服工具／镜子＋决策辅助）· 语言（根因/聚类/影响／订单为什么少、这方案我认不认）。
- **省力的做法**：四列形状几乎可留，换的是**人称和动词**——顾问那列在转述（「客户说要 X」），客户那列在主张（「我要 X」）。随之三改：人称（团队→我们）、信息密度（顾问求全→CEO 求准，CEO 板是**筛子不是账本**）、权威（「确认状态」消失——主张即立场，没有第二个人来批）。
- **盲点提醒**：客户不会替你干顾问的活——别把分析工序搬给客户（那是转嫁负担）。突出客户＝**做减法**：客户只面对「我的事实、我要定的、我在做的」。
- **「这页面白做了吗」的判断法**：机制层留（卡片＝一条事实、卡片引用成链、离线＋同步、工作区隔离），语义层重写（四阶段语义、卡片类型与字段是顾问方法论的产物）。**占位结构 ≠ 产品**——产品文档已写「信息结构是可调整的积木」，硬编码的阶段从一开始就是占位；舍不得占位、把顾问流程硬塞给客户，才是真损失。

完整四轴分析、CEO 看板四列映射、以及 fixture 里「顾问诊断口吻 → CEO 立场」的改写实例：`references/consultant-vs-client-view.md`

## 反模式（案例库）

| 反模式 | 案例 | 正确做法 |
|--------|------|---------|
| 转译概念 | "收集/澄清/结构"替代 4D | 直接用 感知/理解/预测/决策 |
| 名词任务 | "清晰度判断"/"本体挂接" | "判断清晰度"/"挂接本体" |
| 任务性质错位 | 预测活动写"挂接本体/升级模式"（结构组织≠推演） | 任务匹配活动本质（推演类：识别模式/推演走向） |
| 含糊概念 | "对照本体"/"确立目标(无交互)" | 移除或明确交互（AI 候选+用户确认） |
| 需求外发明 | 本体树/挂接/升级（需求无对应） | 砍 |
| 全量规划 | 预测/决策页无数据就做 | 最小闭环先行，延迟验证 |
| 档案记现状 | 组件状态矩阵/用户流程档案 | 档案记**理想交互体验**（目标状态） |
| 聚合过度建模 | 事件风暴四聚合（JournalEntry/Business/ProfileItem/Distillation） | 核心实体最小化（Task + TaskList）；清单是视图不是实体 |
| 冗余字段 | Task.blockReason（被问"是什么"） | 阻塞=status 一种（blocked）；原因记 content；title 与 content 分开 |
| 清单当视图 | "清单是视图不是实体" | 清单=业务实体+职能 Group 分组（飞书/滴答同构、与档案同构） |
| 静态假设 | 清单固定三 Tab（qtdata/qtclass/qtcloud） | 数据驱动的动态清单切换器（不硬编码，业务可扩展） |
| 自创词 | 分组叫 Section（受现有代码影响） | 用 Group（与"分组"心智一致） |
| 泛化字段 | content（"内容"太泛） | 任务领域惯例 title+description |
| 发明层 | services/ 放 AI 加工 | 归入 repositories/（数据访问）；模型 models/、仓储 repositories/ |
| 详情独立页 | 任务详情单独路由页 | 弹窗组件（views/）清单内就地打开 |

## 设计档案规范（quanttide-design profile）

- 产品一级文件夹 + index.md（如 `profile/qtcloud-product/index.md`）
- 内容 = **理想的交互设计体验**（打开时/操作时/结束时应该是什么感受），不记现状
- 体验优先、随理解更新，不追求一次写全
