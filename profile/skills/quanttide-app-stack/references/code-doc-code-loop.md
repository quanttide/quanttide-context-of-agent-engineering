# 代码-文档-代码循环（qtcloud-code 重设计方向）

> 用户确认的设计蓝图（2026-08-16）+ 实验室验证实验（quanttide-laboratory-of-software-engineering，五标准全过）。

## 蓝图（用户确认）

qtcloud-code（量潮编程云）重新设计为**代码-文档-代码的循环**，用**文档驱动 + 测试驱动**：

```
    ┌──────────────┐
    ▼              │
 代码 ──提取──→ 文档     代码 → 文档：文档是代码的镜像（自动生成/同步，永不过时）
  │              │
  │              ▼
 测试 ←──校验── 文档     文档 → 代码：规格驱动实现（DRD/契约先行，TDD 落地）
  │              │
  └──红灯→更新───┘      测试 → 闭环：测试校验"文档说的"与"代码做的"一致
```

三个环节：
1. **代码 → 文档**（提取）：从代码库提取结构事实（函数/类/模块图——qtcloud-code v0.2.1 已有 multi-language graph def/func/function 基础）→ 生成/更新文档
2. **文档 → 代码**（驱动）：文档（规格/契约）定义期望 → 测试先写（TDD 红灯）→ 代码实现转绿
3. **测试 → 校验**（闭环）：**文档-代码契约测试**——文档声明的 API/行为 vs 代码实际导出——不一致即红灯

循环动力：代码演进 → 文档过时 → 契约测试红灯 → 更新文档 → 驱动下一轮。

## 定位修正：约束驱动生成（用户两次澄清，2026-08-16）

**CLI 的设想是"约束性的"——约束 AI 最终交付的代码、测试、文档对齐**（不是文档生成工具）。随后精确为"**用约束驱动生成**"——不是事后门禁：

| | 事后校验（误读） | **约束驱动生成（用户确认）** |
|--|----------------|------------------------------|
| 约束时机 | 生成之后检查 | **生成之前定义**（任务是约束文件的一部分） |
| 约束角色 | 验收清单 | **生成规范**（AI 的输入约束，引导生成） |
| 校验作用 | 拒绝 | **反馈回路**（差异 → AI 带反馈修正 → 再生成） |

约束 = AI 任务的规格输入（contract.yaml：code/test/doc 契约）；工作流 = 任务(约束) → AI 生成三件套 → 校验 → 红灯给结构化差异 → AI 修正 → 绿交付。

## 命令命名：audit（不是 verify / review）

用户问过 verify vs review、verify vs audit，结论 **audit**：

- **audit > review**：review 是主观质量审查（风格/设计，需人/LLM 判断）；audit 是**系统性检查发现问题清单**（对齐是可判定的客观检查）。量潮 review 语义已被 `devops-review` skill（流程审查）占用
- **audit > verify**：verify 输出"通过/失败"二分，对 AI 反馈信息量不足；audit 输出**问题清单**（每个差距可定位）——**清单即 AI 的修正任务**（约束驱动生成反馈环的核心）。且量潮已有 audit 惯例：`qtcloud-devops release audit`（发布预检）+ `code-audit` skill——audit = 量潮的"检查门禁"词汇

## audit + 3R 架构（qtcloud-code CLI docs 已更新，2026-08-16）

qtcloud-code CLI 现有 3R 架构（review→reflect→refactor，见 src/cli/docs/dev/）——audit 作为**前置交付约束层**：

```
audit ──→ review ──→ reflect ──→ refactor
 │           │           │           └─ patch（代码修改）
 │           │           └─ 理解层（LLM 分析）
 │           └─ 检测层（规则引擎 + LLM）
 └─ 交付约束层（对齐校验——代码↔测试↔文档，约束驱动生成）
```

**三边审计规则**：
1. 代码 ↔ 文档：API 完整（双向）+ 签名一致（提取器 AST ↔ 文档声明——实验已验证）
2. 代码 ↔ 测试：测试引用的 API 存在且签名一致（静态分析测试引用）
3. 测试 ↔ 文档：文档声明的每个 API 在测试中出现（有测试验证）

输出：问题清单 `{类型, API, 位置, 期望, 实际}`（机器可读 --json 供 AI 消费）；退出码 0/1 可入 CI（合并前 audit 必须绿）。audit 只读不改代码；下层不能跳过（audit 不过不进 review）。

## 3R 查证与体系收敛（2026-08-16 最终版）

用户先后问"reflect 总体没有发挥什么作用…帮我确认一下是不是""refactor 也类似"——**查证后减法收敛**，最终架构：

```
交付约束体系（双约束核心 + AI 直接修复）：
  audit   ✅ 对齐约束（代码↔测试↔文档）——机器可判定，CI 门禁
  review  ✅ 质量约束（代码问题）——规则引擎兜底 + LLM
  修复     = 问题清单 → AI 直接按清单修正（不依赖 CLI 修复命令）

降级/移除：
  reflect ⚠️ 独立定向分析工具（slice/trace/graph/suggest，人类偶尔用）
  refactor ❌ 已移除
```

**查证工具实际价值的方法**（减法决策的证据链）：
1. **实现 vs 设计差距**：refactor 文档描绘"提取函数/内联/死代码删除 + LLM 策略"——实现只有 `rename`（src/refactor/ 仅 rename.rs）→ 设计≫实现即"被架空"信号
2. **使用痕迹**：修复主路径实际由 `review --mode deep`（LLM patch）与 AI 直接修正承担——命令从未参与真实工作流
3. **流程角色**：reflect 服务"人类做定向分析"（slice/trace/graph/suggest）——真实流程是"AI 修 AI"，人类不跑 → 技术完整但无消费方
4. **判定标准**：命令在真实工作流中是否有**不可替代的消费点**——没有就降级/移除（减法优先，文档标注状态与理由，不硬删历史）

**交互教训**（用户纠正"我是问你觉得是否需要淘汰"）：用户说"X 十分需要淘汰"这类**判断性陈述也可能是征询判断**——先给出查证后的判断 + 建议，**确认后再执行结构性删除**，不要直接动手（本会话曾误执行删除 5 个文档，随后恢复重构）。
