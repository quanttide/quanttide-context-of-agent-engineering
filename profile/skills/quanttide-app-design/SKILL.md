# 量潮应用设计工作流

## 目标

为量潮产品（qtcloud-think/qtcloud-agent/qthealth/qtcloud-product 等）从需求到设计到实施的完整工作流——产出可信赖的设计文档与可实施的清单，避免"细节理解偏差"与过度设计。

## 流程（四层文档 + 两步实施）

### 第一步：需求地图（data/profile/<app>/requirement.md）

按 product-requirement SKILL 标准（用户画像 + 活动描述段 + 任务 + 故事）。**任务必须是动作**：`### 任务：[动词+名词]`（"判断清晰度"✓，"清晰度判断"✗）。

### 第二步：设计文档（src/<端>/doc/）

```
doc/
├── index.md              # 模块设计（定位/模块结构/数据流/实施分解）
├── models/<model>.md     # 模型设计（字段/状态流转/序列化）
├── screens/<name>.md     # 页面设计（功能区布局/交互行为/数据/测试）
├── views/<component>.md  # 组件设计（弹窗/卡片/看板——非页面的复用单元）
└── states/<name>.md      # 状态层设计（Bloc/Cubit 划分、数据流）
```

每个模块文档含：定位 + 设计/接口 + 数据 + **测试设计**（用例列表）+ 验收。

- **页面 vs 组件（用户纠正）**：能做组件的不配页面——详情用弹窗（TaskDetailDialog），清单内点击弹窗打开，不跳页。screens=路由级页面，views=组件
- **两级导航合并为单页分栏（2026-08-23 qtcloud-docs 实证）**：TOC 页 + 内容页拆两个页面是"页面导航思维"——"一本书 = 目录 + 正文是一体的"（Notion/语雀/Obsidian 分栏）。文档集/书级：**单页分栏**（桌面左 TOC + 右内容，手机 TOC 折叠为抽屉），选中章节内容区切换——screens 收敛为最少（文档集列表页 + 文档集单页），Cubit 相应合并（章节目录 + 当前章节 + 模式一个 Cubit）
- **pi 分阶段执行（2026-08-23 实证）**：设计文档定稿后调 pi 按 ROADMAP 分阶段实施（领域层→状态层→组件层→页面收敛），每阶段任务描述必须含：读哪些文件、产出哪些文件、**"只改阶段 X 不碰其他"约束**、验证命令（`export PATH=$HOME/flutter/bin:$PATH` + analyze/test）；pi 沙箱 gitdir 只读——文件改完 Hermes 验证 + 分层提交；**pi 会自编 seed/测试数据——用户数据优先替换后需修 pi 的测试断言**（硬编码任务 id/数量）；每阶段 pi 完成后 Hermes 复跑 analyze/test 再提交

**状态层命名**：`states/`（概念名）而非 `blocs/`（绑定 flutter_bloc 库）——换库不换名。

**事件风暴（DDD）**：大功能先做事件风暴 → `docs/specification.md`（领域事件/命令/聚合/角色/事件流/设计约束）——聚合与字段逐项审核（见设计原则 6）。

### 第三步：TODO.md（实施清单）

按实施分解列出可勾选任务（分解 1-N + 验收项）。

### 第四步：实施（分两步，旧代码全丢）

1. **单元测试部分先行**：models + repositories（纯 Dart 逻辑 + 单测）
2. **组件测试部分后行**：screens + 导航壳（widget tests）
3. 旧方案代码直接删除，不迁移（"旧代码可以全部丢弃"）

### user-guide 双形态写作（2026-08-24 qtcloud-crowd 实证）

给新应用写 user-guide（面向非开发者读者）时用**双形态**：每个功能写「想象中的样子」（完整形态——管理界面/流程全貌）+「最精简的样子」（最小闭环——先做哪个，一个动作/两个判断）+「精简理由」。用户会逐条收敛（"哪些可以精简"）——主动用尺子过一遍：砍没验证的仪表盘（"镜子不是仪表盘"）、合并同类概念（结算单/台账→结算记录）、远期功能一句带过（信用）。管理类工具文档按**人-财-事三视角**组织（执行方/结算/任务——用户确认"刚好是人财事三个视角"），文件名用简洁单词（partners/settlement/review——"像 settlement 统一"）。dev-guide 从 user-guide 的"最精简的样子"出发做实施顺序——**最精简即实施起点**。**人类友好写作（2026-08-26 qtcrowd provider.md 实证——用户"注意人类友好"）**：给非开发者/维护者读的实现方案文档用**人话 + 类比**——服务定位一句话说清（如"前台写操作的门卫——认领/交付经它转交后台"）、每个配置项配一句人话解释（不是参数表）、转交规则用"后台怎么说前台怎么听到"描述、明确"不做的事"（不读列表/不做审核）。类比可复用：门卫/金库钥匙（转发代理）、注册表/发现（OSS 桶发布-读取）。

### 端角色与 site 定位（2026-08-24 qtcrowd/qtcloud-crowd 实证）

- **先问"这个端给谁用"再设计**：同名端在不同产品角色不同——`qtcrowd studio`=**众包参与人员端**（认领/交付/结算查看）、`qtcloud-crowd studio`=**管理方端**（人财事审核）——初始化前先确认使用者（管理方/参与方/公众），否则方向全错（曾把参与端当管理端做）。用户确认句式："qtcrowd studio 是给众包参与人员使用的"
- **site 默认功能介绍页（无数据模型）**：给 site 派任务（含 pi 任务描述）时**不要塞数据模型/管理流程**——"site 是介绍功能的，不应该有数据模型"（用户纠正）——hero + 功能卡片一句话即可；只有用户明确"展示真实数据"才从 provider 拉（如"众包 site 要展示众包信息"+确认"真实数据"后，site 依赖 provider GET API 只读展示任务池）
- **数据边界**：参与端本地数据（我的认领/结算，本地文件原子写）与管理端数据（provider 台账）分离；两端共用同一 provider（唯一服务端数据入口）——site 静态不依赖；cli 直读同构数据文件

### 多端架构决策（2026-08-26 qtcrowd/qtcloud-crowd 实证——用户主导的决策链）

**双 provider 独立（管理私有/前台公开）**：管理端（qtcloud-crowd）与参与端（qtcrowd）各自独立 provider——理由：①数据模型不同构（管理：验收准则/审核状态 vs 黄页：报酬/报名引导）②安全边界（公开流量不打内部管理服务）③推送即发布语义。判断标准一条：**参与端是否对外开放**——对外=独立，内部用=复用。

**依赖方向硬约束：前台可以依赖后台，反之不行**——由此同步方式定为**拉式**（前台拉后台 published 任务）而非推式（后台调前台 API=后台依赖前台）。但用户指出拉式丢\"推\"语义 → 评估事件总线/Outbox/OSS 直写三种，最终：**OSS 即最轻的注册模式**（后台写公开桶对象=注册/发布，前台读桶=发现——零额外基础设施，不引 MQ；完整注册中心 Consul 那种才是\"太重\"的）。

**公开数据层属前台自有（最后修正）**：后台**不要自己建公开桶让前台读**（前台依赖后台基础设施=错）——正确：**前台 provider 拥有自己的对象存储**，后台发布=提交（OSS 写入）到前台的桶；site/studio 读自己的桶（CDN），认领/交付写经前台 provider（轻量转发代理——不直连后台，透传 404/409/400/502 状态码，租户上下文预留）。前台写操作必须经自己的 provider（前台薄壳：读 CDN + 转发写——直连后台=暴露后台地址+无租户上下文）。

**定稿终态（2026-08-26 二次修正——上架模式）**：qtcrowd-provider **调用 qtcloud-crowd-provider 的 API 上架**（前台主动拉取/上架——后台只响应），数据存在**自己的 OSS 桶**（配套命名：qtcrowd-provider 桶——C 方案，与后台桶配套命名），并**通过 API 给 site/studio 提供数据**（读也经 provider——site/studio 不再直读 OSS/CDN）——前台 provider 是前台唯一服务端（上架 + 数据 API + 写转发）。后台不建任何公开桶（公开层不在后台图纸）。

**图纸纪律（用户三次纠正\"不在我的设计图纸上\"）**：实现架构前**先完整确认图纸上的资源清单**（桶/服务/域名/文件）——只实现图纸内的，**不发明图纸外的资源**。反例（2026-08-26 全部被纠正）：①后台 terraform 建公开桶（\"4 不保留，这不在我的设计图纸中\"）②qtcrowd 新建 terraform 桶 IaC（\"2 不对，也不在我的图纸上\"）③新建 qtcrowd-public 桶（\"只删除不新建\"）。用户图纸 = site/studio/provider **各自对应的存储桶**——多余桶/多余 IaC 都是发明。被纠正后：删除多余资源（`aliyun oss rm oss://<bucket> -r -f` 清对象 + `echo y | aliyun oss rm oss://<bucket> --bucket` 删桶），不新建替代。

**多租户预留（设计预留，代码不做）**：路径/目录/API 路由**不写死单租户假设**——公开层 `public/tasks/`→`public/{tenant}/tasks/`、私有层 `data/crowd.json`→`data/{tenant}/crowd.json`、API `/api/tasks/`→`/api/{tenant}/tasks/`——新租户市场=新前缀+新前台实例；现在不写多租户逻辑（验证先行），只留扩展缝。

**架构决策文档化**：定稿后写进 dev-guide/index.md 架构章节（依赖方向硬约束/桶设计/数据流/多租户预留表）——pi 实施严格按文档（\"文档怎么写 pi 怎么做\"），实现偏离架构图（如跳过 qtcrowd provider 直连后台）要在 review 时抓出。

**验收标准层级模型（2026-08-26 qtcloud-course 实证——用户\"验收标准\"和场景或者课时关联哪个更合适）**：验收标准两层——**最小操作单元级**（Scene：每步完成判定——学员做每步立刻知道对不对）+ **组织单元级总验收**（Lesson：场景全过 + 跨单元约束如安全/合规）——两层**同构**（`Acceptance{criteria, method, on_fail}`——一个结构复用）。**中间层不加**（Course 级验收=课时全过，重复无新增语义——\"课程的完成标志更像课程目标/产出而非验收判定机制\"——说不清就砍）。演进条件：出现**跨单元约束**（整门课成果必须提交仓库——不属于任何单课时）时才给中间层加同构字段（一行扩展不重构）。实现落点：**改 provider 模型（domain + JSON 字段 + data-model.md 文档 + roundtrip 测试），不是改 profile 创作档案**（用户纠正\"改 provider，不是 profile\"——验收模型是服务端能力）。

## 设计原则（用户强约束，违反即被纠正）

1. **结构即真实**：直接用原始概念（如 4D 认知过程→导航直接用"感知/理解/预测/决策"），**不发明转译层/抽象层**（"收集/澄清/结构"✗）
2. **语义诚实**：每个概念必须能说清"用户做什么"（是动作、可操作）；**说不清就砍**（"对照本体"→移除）
3. **需求地图是法源**：界面不发明需求地图没有的任务（本体树/挂接/升级因需求无对应任务被砍）
4. **验证先行**：最小闭环（高频路径）→ 真实使用 1-2 周（主动用/缺了难受=值得做）→ 砍掉验证（砍了不影响=不值得做）→ 数据驱动（死功能砍）。**高级功能延迟**到数据积累后再判断（无实例数据的预测页=空壳）
5. **认知工具闭环到"决策"**：4D 第四环选"决策"（认知判断产出）非"行动"（现实执行——越界）
6. **聚合/字段最小化（事件风暴收敛）**：聚合能少就少（执行云 4 个聚合 → **Task + TaskList 两个足够**）；字段逐项审核——每个字段必须能说清用途，说不清就砍（blockReason/source 被砍），命名用领域惯例（**title+description** 而非 content；枚举明确：status 四态/priority 四档；**Group** 而非 Section）。**容器/子级命名同词根对齐（2026-08-23 qtcloud-docs 实证）**：书级容器叫 `Book` 与单篇 `Document` 不对齐（两套词根）——用 **DocumentSet + Document**（同词根、少歧义）；备选先查领域真实术语（文档工程：Docset/Publication/Part）再定
7. **数据驱动，不静态假设**：清单/列表从数据加载（"三个业务 Tab"被否——业务会扩展），用动态切换器；固定枚举只用于真正不变的维度（状态四态）
8. **看板 = 状态泳道（最终确认）**：列=状态（未开始→进行中→评审中→已完成四泳道），卡片列内纵向堆叠、**拖拽跨列=状态推进**——这是 Kanban 本质。用户中途确认过"列=分组、行=状态"，但最终发现"状态调整到列更合适"、分组放列内"意义有限还干扰"→ **取消 TaskGroup，降级为 `Task.category` 字段（String，业务自定义分类，不枚举约束）**——分组不占任何视觉结构，只作可选筛选
9. **先交互范式，后数据结构（BoardView 表格化教训）**：设计看板类交互，必须先想"用户怎么用"（泳道/流动/拖拽推进），再定数据结构。反例：BoardProjection 用 `Map<Group, Map<Status, List>>` 矩阵投影 → 实现必然渲染成 Table（行列交叉定位）——**数据形状定义了产品形态**。且设计文档用什么语言，实现就长什么样（doc/views/board_view.md 通篇"矩阵/单元格/交叉定位"→ pi 按文档实现表格）——文档必须用目标交互范式语言（泳道/堆叠/流动），不能用投影/网格语言。镜子原则 ≠ 数据投影=UI：成熟交互范式（Kanban/Trello）直接采用，不因"结构即真实"自创布局。**复盘纪律（用户纠正"反思方向不对"）**：复盘失败时不要用"用户确认过布局指令"来豁免自己的设计责任——布局是用户给的，但**设计起点（从数据结构出发而非交互范式）是自己的**——方向错就是错，往自己身上找，不推给确认过决策的用户。**诊断顺序（"怎么更不正常了"后用户质询"你是怎么理解上一轮任务的"）**：用户报异常后先**确认实际症状**（问/复现：空白？重复？翻不了页？），再定位病因——跳过"确认症状"直接"推断病因"（修的是猜的 bug 而非验证的 bug）会被视为不诚实；无法真机复现时明说"修的是推断点"，并给回退选项（简化/回退到稳定方案）
10. **自适应 ≠ 响应式（用户纠正）**：手机端适配是**设备决定交互形态**（`pointer: coarse` 检测 → 双模式组件：手机=PagedReader 分页翻页、桌面=ScrollReader 连续滚动），不是同一布局随宽度缩放（media query 断点=响应式）。用户要"自适应"时给双模式分支（`{isTouch ? <PagedReader/> : <ScrollReader/>}`），不要只写断点 CSS。功能范围同理收敛："能正常阅读就可以"→ 砍掉专业阅读器功能（字体/划线笔记/设置面板/同步），只做核心阅读（排版+翻页+进度）。**实现坑（"怎么更不正常了"根因）**：`pointer: coarse` 在**触屏笔记本也匹配**——移动端判定必须 `coarse && 窄屏(<768)` 双条件，否则宽屏触屏设备误入分页模式（每页占满全屏宽、无法阅读）；**发布后必须在目标设备形态下验证交互**（curl 200 只证明页面可加载——双模式体验要手机/触屏视口实测，本地可用 dev server + 窄视口验证）

## 结构规范（对齐现有仓库惯例）

- **Flutter lib 三件套**：`models/ + repositories/ + screens/`（对齐 qtcloud-agent），**不发明 services/domain/infrastructure 层**（除非用户明确要 DDD）
- **仓储 = DDD Repository 模式**（接口封装数据访问），不是"数据存放位置"；种子数据（assets/data，git 跟踪）vs 用户数据（~/.xxx，忽略）是存储位置问题，与仓储概念无关
- **profile 档案记稳定记录**，不记任务清单（tasks/ 删除——动态任务进 roadmap/journal）
- **UI/UX 分析归档归属（用户纠正）**：交互体验/UI 分析归 `quanttide-design` 的 data/context（交互设计语境），不归产品领域 context——产品 context 只留产品研发内容
- .gitignore 用**精确路径**（`/src/studio/data/`），裸 `data/` 会误伤 doc 文档

## 实施陷阱（2026-08-22 qtcloud-think 分解 1 实证）

- **改 Dart 代码用 patch 不用 sed**：sed 批量替换会改坏字符串（曾把 `jsonEncode({'content': ...})` 弄成 `jsonEncode({"'\"content\"'": ...})` 报 `ambiguous_set_or_map_literal_both`）——编译错误后 read_file 定位坏行，用 patch 精确修复
- **测试局部辅助函数不要 `_` 前缀**（`_thought()` → `makeThought()`）：`no_leading_underscores_for_local_identifiers` lint 会报；改名后要 `grep -rn` 全部调用点，sed 只替换声明会留一半旧名（undefined_function）
- **`implements` 接口时记得 `@override` 注解**（annotate_overrides lint）
- **字符串插值包变量**（`'$var'` 而非 `'${var}'`）——`unnecessary_string_interpolations` lint
- 仓储测试用 `Directory.systemTemp.createTempSync()` 注入临时目录（不碰真实 ~/.xxx）；AI 访问仓储用 `MockClient`（http 包）拦截断言 URL/body
- **flutter test 资产打包不递归子目录**（2026-08-23 qtcloud-docs 实证）：种子数据重组为 `assets/data/docsets/`+`documents/` 子目录后，flutter test 的资产打包器对目录条目不递归——测试报资产缺失。修复：**pubspec.yaml 显式列出每个种子文件**（注释\"新增标本需登记\"），不要用 `assets/data/` 目录通配

## 验收标准

- [ ] 需求地图：任务全是动作、活动是用户旅程、故事"用户要…"
- [ ] doc 与代码结构一致（doc 引用路径 = 实际目录）
- [ ] 测试设计并入各模块文档
- [ ] 实施后 analyze 零问题 + 测试全过 + build web 成功
