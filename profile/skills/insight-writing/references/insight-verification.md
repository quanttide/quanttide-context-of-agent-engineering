# 最小成本验证洞察：实证与操作细节

来源：2026-09-12 会话（code 域 `data/insight/programming-agent.md` 的首次验证）。用户问"如何以最小的成本验证洞察？"，随后指定"journal 和 profile 有丰富的证据可以验证，选择一个合适的"——本篇记录方法与那次验证的完整走法。

## 一、方法骨架

判断验证是否划算，只问一句：**这个验证要不要"专门做点什么"？** 要，就先怀疑它不值得做。

| 证据类型 | 成本 | 做法 |
|---|---|---|
| 已经发生的 | 0 | 翻存量：journal / report / profile / 案例库 / 聊天记录 |
| 未来必然发生的 | ≈0 | 搭车：挂到反正要做的工作上，事先埋观测点 |
| 为别的目的本来要做的 | 已付 | 真实使用，验证是副产品 |
| 为验证专门造的 | 高 | 先放一放；多半说明行动差小 |

## 二、证据源的选择（用户给的判据）

- **优先一手自述**：journal 里当事人当时的诊断（"我建的模型，我不知道对于真实业务可不可靠"）> profile 的整理稿（已经是加工过的描述）
- **profile 词汇密度作旁证**：某词在领域档案里反复出现，即该处消耗最大。code 域实证：「对齐」出现在"v0.1.0 对齐阶段""镜像边界清晰""契约与实现对齐""契约权威在 toolkit tests/fixtures"——对齐是反复出现的动作甚至工作阶段。词频即成本
- **一次只选一个主证据**：主证据 + 旁证，别堆一串（堆料会让判定失焦）

## 三、把预测改写成可数形式（改写表）

| 写不出来的 | 数得出来的 |
|---|---|
| 对齐是编程的瓶颈 | 每次任务里人介入的原因分布（对齐类 vs 流程类） |
| AI 产物质量差 | 同任务的改稿轮次 |
| 流程破碎 | 一次任务跨手的系统个数 |
| 反馈循环缺失 | 交付时有无判据（有判据=闭合；靠事后返工才发现=缺失） |

## 四、实证走法（code 域，成本实测）

1. **选主证据**：`data/journal/qtcloud-course/2026-08-27.md`（全文 13 行，一手自述）
2. **旁证**：`grep -rn "对齐|建模|字段" data/profile/`（一次 grep）
3. **判定表**（写进洞察文件的「验证记录」节）：

| 断言 | 证据 | 判定 |
|---|---|---|
| 瓶颈不在生成，在对齐 | 「团队层面的生产效率有很大一部分还是幻觉，很多关键且非常精密的调整，还是需要我自己来动」 | 支持 |
| AI 建的模型与业务对不上 | 「团队层面对于字段级别的建模明显不足」 | 支持 |
| 人类自己的模型未必对 | 「我建的模型，我不知道对于真实业务可不可靠」 | 支持（最强） |
| 单向对齐不成立，需对比 | 由上条推论 | 收窄后支持 |
| 工作流不是核心 | 规模化产出仍是幻觉；工程标准靠换模型而非改流程 | **弱支持（旁证）——如实标注** |

4. **副产品（比结论更值钱）**：
   - 收窄出**可测形式**：对齐难 → "反馈循环缺失"（可数）
   - **修正原判断**：原洞察说"观察者最缺"，验证发现已有雏形——`profile/qtcloud-execute/studio.md` 的建模原则「AI 建议 + 人确认，AI 不直接修改（判断不是事实）」
   - 找到**闭环手段**：用例设计让循环闭合（接上 work 域"案例库→用例"）

## 五、写进洞察的形态

```markdown
## 验证记录

**<日期> 首次验证（零成本，翻存量证据）**：证据取 `journal/...`（一手自述），旁证取 `profile/` 词汇密度。

| 断言 | 证据 | 判定 |
|---|---|---|
| ... | 「原文引句」 | 支持 / 收窄后支持 / 弱支持（旁证） |
```

- 引句保留原文（可回溯），不转述
- 弱支持必须标"弱支持（旁证）"，别把旁证写成直证
- 验证后同步该洞察的正文（可测形式、修正的断言），别只追加记录节

## 六、下一步该做的（验证闭环）

拿到一次支持 ≠ 验证完成。把"搭车验证"埋进本来要跑的工作流（如 `code-implement` 加一条计数判据：人介入分对齐类/流程类），跑几轮取多例；证伪时限到期走回声三处置（证实升格 / 证伪归因 / 问题消失归档）。
