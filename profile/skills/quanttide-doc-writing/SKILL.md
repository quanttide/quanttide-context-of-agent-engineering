# 量潮文档写作

写设计文档、架构文档、README、ROADMAP 等技术文档时的写作规范。多次被用户纠正后沉淀。

## 叙事逻辑

按**读者的问题顺序**写，不按架构/代码展开顺序写：

1. **解决什么问题**——痛点，为什么现有方案不行
2. **洞察/发现**——核心认识，凭什么这么设计
3. **怎么做**——解法，具体机制
4. **验证/普遍性**——证据，还有什么也适用
5. **落地**——怎么用，各模块入口

**反面**：按架构顺序平铺（功能定位→模块 A→模块 B→…），最有价值的东西藏在最后一节当附录。

## 禁用自造概念

不发明口语化的复合词当术语。反面例子（用户明确否掉的）：

- ~~同构~~ → 「结构相同」「同一套组织方式」
- ~~三层管线~~ → 「分三步：语法解析、结构切分、语义提取」
- ~~读懂层~~ → 直接说「让 AI 理解语义」

**判断标准**：如果一个词需要额外解释才能懂，它就不是好术语。用现成的、朴素的说法。

## 读者视角

- **先给例子再讲道理**：贴一个「进→出」的对照（输入文件→解析结果），读者先看到效果再看原理
- **每节回答一个读者问题**，不回答「我们做了什么」
- **自造概念首次出现必须就地解释**，不留给后面
- 三种文体不混：README（是什么）、设计文档（为什么）、API 参考（怎么用）——一篇文章只干一件事

## 本质优先

用户问「一句话说这是什么」时，回答要到**目的层**，不停在手段层：

- 反面：「把 Markdown 变成结构化数据」（手段）
- 反面：「规则说怎么读，LLM 照着提取」（手段）
- 反面：「人用目录表达结构，工具让 AI 照着理解」（仍是手段）
- 正面：「人和 AI 在同一套知识结构上读写，还能在上面计算」（目的）

**追问测试**：如果回答的还是「怎么做」而不是「为了什么」，就还不够本质。

## 简繁判断

- 一个文件一类角色，一个目录才有意义时才建目录
- 十来个文件不配五个目录——「这什么玩意」= 过度设计
- 小类（几十行）不一文件一个
- 分层方案给出来后先问：切分轴一致吗？每个目录都有存在理由吗？

## 平台/概念不混淆

不同平台、不同系统是不同实体——描述前先确认「这是同一个东西吗」。用户说「不是同一个平台，搞混了」= 概念边界错了，先厘清再写。

## 精简既有文档

用户说「精简 X.md」时，不是压缩措辞，是**按归属重新分工**。删四类：

| 删什么 | 判据 | 实例 |
|---|---|---|
| **失效的** | 引用的路径/流程已不存在 | CONTRIBUTING 的「同步 SKILL 到 gallery」指向 `docs/gallery/devops/`——该目录根本不存在 |
| **不符本仓的** | 照抄通用模板，与本仓实际相反 | CONTRIBUTING 写「建分支→PR」，而本仓是子模块架构 + 提交即推送 |
| **重复的** | 同一件事写两遍，或已有更全载体 | 「新增子模块时」与「子模块维护/新增挂载」；构建部署细节已在 `docs-deploy` skill |
| **通用的** | 任何项目都成立的空话 | 「记录问题→分析原因→修复→更新文档→持续改进」五步 |

删完之后按归属分流，不留原地：

- 本仓**特有约定**（别人照抄会错的东西）→ 留
- 通用流程 → 指向外部规范
- 操作步骤 → 归 `.agents/skills/`
- AI 工作经验 → 归 `AGENTS.md`

**两条硬纪律**：

1. **删前查内容是否已有正式归属**——STATUS 的「qtdata 差距分析」已在 `data/insight/index.md`（全景）+ `qtdata/intention-gap.md`（细节），删的是复述，不是内容。删完还要**修反向悬空引用**（insight 里写着「STATUS 文档已做差距分析」→ 改成指向自身）。
2. **精简时不要照搬被精简文档里的路径**——旧 CONTRIBUTING 把门户写成 `docs/index.md`、`docs/myst.yml`，实际都在**仓库根目录**；照搬即继承错误。文中每个路径/文件名都要实测（`ls`）再写。用户标准：文件名/参数一律从代码或真实数据抄。

实证：章程 17→14 条；CONTRIBUTING 134→38 行；STATUS 19→13 行。
