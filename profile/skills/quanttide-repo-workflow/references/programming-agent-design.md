# 编程智能体设计立场（quanttide-code/data/context/iGuo/2026-09-12）

用户 2026-09-12 在 code 域语境里给出的判断，是 code 域（qtcloud-code / 编程智能体）后续设计的依据。

## 核心命题

- **知识工作那套流程化范式不适合处理编程**：规范流程只能保证产出"尽量靠近人类理解范围"，不能保证写出来的东西科学合理
- **优先级**：纠正很重要，但**首先要保证能用**；"能用"到"好用"之间有距离，要控制这个距离
- **真正瓶颈不是生成代码，而是对齐**：AI 会发明人类不知道的概念/结构/模型；人类脑中的模型又未必正确 → 须把"人类意图模型"与"AI 实际建的模型"对比，甚至反过来**先写代码，后治理**
- 对齐带来巨大理解负担，**不是串联工作流能解决的** → **工作流不再是产品核心**（至少不是交互核心）。与知识工作的分界：知识工作处理大量琐碎碎片（流程有效），编程是复杂系统构建（对齐有效）
- 现状：已有"实验室 + 平台 + 工具库"范式，勉强可用，但**摩擦大、低效，摩擦点就在对齐**

## 产品形态方向

**内置 harness 机制**——上层交互极简、极符合直觉，**所有复杂性放进 harness 骨架**，由骨架驱动内部单元合理分工；据此构建一个更高层次、专做复杂系统构建、追求**高一致性**的编程智能体。

两个单元：

1. **生成器**（写代码的单元）：自由探索、建模、实现，先保证系统能跑
2. **对齐机制**（理解代码并与人类对齐）：解释、映射、对比、重构理解——把 AI 的隐式模型**外化成人类可审查、可干预的结构**

架构名：**探索者-观察者架构**，其中**观察者需要专门设计**。

## 首次验证结果（2026-09-12，零成本，已写进该 insight 的「验证记录」节）

用户问\"如何以最小的成本验证洞察\"→ 指定\"journal 和 profile 有丰富的证据可以验证，选择一个合适的\"。方法与判定表见 insight-writing 技能的 `references/insight-verification.md`。结论：

- **主证据**：`data/journal/qtcloud-course/2026-08-27.md`（一手自述）——\"团队层面的生产效率有很大一部分还是幻觉，很多关键且非常精密的调整还是需要我自己来动\"、\"字段级别的建模明显不足\"、**\"我建的模型，我不知道对于真实业务可不可靠\"**（人类模型未必对 → 支持\"先写代码后治理\"）
- **旁证**：`data/profile/` 的「对齐」词汇密度（v0.1.0 对齐阶段 / 镜像边界清晰 / 契约与实现对齐 / 契约权威在 toolkit tests/fixtures）——对齐是反复出现的动作甚至工作阶段
- **收窄出的可测形式**：**反馈循环缺失**（交付时有无判据：有判据=闭合，靠事后返工才发现=缺失）
- **修正原判断**：\"编程域缺观察者\"应改为**只有雏形**——`profile/qtcloud-execute/studio.md` 已有建模原则「**AI 建议 + 人确认**，AI 不直接修改（判断不是事实）」，即观察者的最小形态

## 第二篇洞察：观察者雏形（2026-09-12 同日，`data/insight/observer-pattern-seed.md`）

用户要求\"展开讲讲你观察到的'观察者模式'的雏形长什么样子，写 insight\"——展开后成篇，四要素 + 一个定位表述全部带出处（写 insight 时**把出处路径写进正文**，可追溯）：

| 要素 | 现场形态 | 出处 |
|---|---|---|
| 判断权与写入权分离 | 「AI 建议 + 人确认」——AI 不直接修改（判断不是事实） | profile/qtcloud-execute/studio.md |
| **清点与判断分离** | 评审第一步「看到」一节只清点、不下判断，**禁写\"混乱/不合理\"这类词、禁编造** | profile/quanttide/workflows/design-review.yaml |
| 中间表示 | **流程草案卡**——步骤清单，每步标执行者（AI/机器/人）与判据条数，人确认后才跑 | apps/qtcloud-work/src/studio/doc/views/chat.md |
| **分歧显性化** | 主诊断一句话**与\"人的第一眼\"对照：一致说理由，不一致说为什么**；拿不准单列、旁枝作附录 | design-review.yaml |
| 定位表述 | 把人类认知负担从「创作」降维为「**司法复核**」 | domains/quanttide-asset/data/context/default/vision.md |

**缺口 = 确认权是单点**：多数工作流的判断点写成\"创始人确认\"（发布放行 / 抽取值不值得 / studio 能否独立），与 08-27 自述\"精密调整还得我自己动\"对上。**可测形式**：数创始人确认点的数量与耗时 + 把关强度（返工/错漏）不降——下降=可分配成立；更多更细=只是把负担结构化，设计失败。

**边界（写成后被用户当场修正，教训通用）**：初稿边界写\"编程工序最难切细，切分是前提\"→ 用户\"**可以切。看看 handbook 是怎么做的。**\"→ 依 handbook 三件与 code-implement 工作流改写边界（切法见 `knowledge-work-artifacts.md` 第十一节）。**纪律：用户用一句证据推翻你写的边界时，当场改那节并写明\"原先判断不成立\"，不要静默保留或只在对话里承认**——洞察是公开仓库里的事实源，留着错边界会被下游引用。
