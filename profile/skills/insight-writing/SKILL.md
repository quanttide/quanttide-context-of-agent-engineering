# 撰写量潮 Insight（预测型洞察）

适用场景：在 insight 仓库（如 quanttide-insight-of-business-entity）撰写或评审洞察文档；以及 journal 整理分流（两阶段模型，见末节）。

## 核心：insight 是预测，不是报告

产出遵循 `感知现实 → 理解抽象 → 合理预测`，预测是核心目的。每篇必须能一句话读出：

> 我们预测 X，可被 Y 证伪，若真则改变 Z。

写不出这句的不是洞察，是日志或散文——回各自的库去。

## 五层价值判据（写作与评审共用）

| 判据 | 一句话检验 | 不及格的样子 |
|---|---|---|
| 可证伪 | 什么事实能推翻它？ | "很重要，要重视" |
| 非显然 | 它违反什么默认假设？ | 论证了一通常识 |
| 行动差 | 证实/证伪后动作有何不同？ | "有趣的观察" |
| 点名 | 它预言了哪个具体做法/环节的死亡？ | 听起来都对，没承担认知风险 |
| 回声 | 证伪时限到期后回头验过吗？ | 写完即遗忘 |

- **点名**是最高判据：预言具体对象（模式/环节/产品）的死亡，敢点自己现有做法才承担认知风险
- **回声**是最终检验：证伪时限写进文件头，到期重审三处置——证实升格（进章程/ROADMAP）/证伪归因/问题消失归档

## 结构模板

```markdown
# <判断句标题>

> 源自 <journal/对话来源一行>。

**预测**：我们预测 X，可被 Y 证伪，若真则改变 Z。

## 机制
（为什么——因果结构，不超过三段）

## 迁移
（证实后的动作：治理/产品/度量分点）

## 边界
（失效条件与前提，诚实写）
```

## 写作纪律

- 证据压缩为一行来源链接，全文留在 journal/history
- 禁止防御性写作：模糊词堆砌、骑墙结构、缓冲短语、过度结构化
- 深化现有概念优先于新造概念——命名前先查组织已有词汇
- 脱敏：产品/技术可公开，人事/客户/治理细节不入（公开仓库）

## 与 ROADMAP 的双向校准

- insight → ROADMAP 三通道：**升格**（证实后进核心判断节；ROADMAP 核心判断必须能引用 insight 依据）/ **预警**（点名某做法将死 → ROADMAP 对应条目加退场标注）/ **回滚**（证伪 → 连带修订引用它的判断）
- ROADMAP → insight 两时机：**验收时回查**（条目验收=检验预测的最强形式）、**偏航时立预测**（执行遇路线图没预料的阻力=新洞察萌芽）
- 机制约束：证伪时限写文件头；index.md 维护到期重审队列；双向引用让失同步可被检查
- **决策双写**：洞察记录判断的同时，业务仓 ROADMAP 同步落结构变更（如集体给予物 → qtclass-private P1 执行主体条款）——"同意"之后判断要变成路线图条款才算落地
- **校准机制已固化进 insight 仓 AGENTS.md**（2026-09-08）：升格/预警/回滚 + 验收/偏航，ROADMAP 核心判断须可引用 insight 依据——写新 ROADMAP 核心判断时反查 insight 仓找依据链

## 根因追问的写法（战略讨论下沉场景）

用户对机制类回答连续追问"不够本质"时，洞察的落点跟着下沉：第一轮答机制（怎么解决）→ 第二轮答为什么依赖人（数据化不足）→ 第三轮才是真根因（**结构本身破碎**——qtclass 流程问题的终答：一个学员旅程横跨十个系统靠肉身缝合，方向=筑河床连续流程）。给 insight 立篇时以最终根因为准，中途层的回答（状态机、自动化）是根因的推论不是根因本身——否则洞察会记在中途层，下次同类问题还会绕路。

## 组织机制系列（盘点式回答的成组模式）

组织机制类问题（"如何引导集体动机""哪些经验利于集体智慧"）的正确产出是**盘点式**：先从既有 insight/journal 盘出已有基石（各配作用机制），再指出缺失机制，最后给可观测的发芽/证伪信号。qtclass 现有四篇构成系列，互相引用：

1. **collective-motive-cultivation**（动机=愿不愿意合）：个人动力=交换，集体动力=共同拥有；引导=改利益流向不做说教；发芽信号="我们决定"替代"我配合"
2. **collective-intelligence-foundation**（智慧=合起来是否更聪明）：信号塔/契约协作/议事档案/环境测谎四基石已具备，缺**判断合成器**——反直觉判据：**分歧显性化是合成器工作的证据，全票一致是空转**（分歧点=信息差所在）
3. **collective-giving-artifacts**（靠什么合起来）：公开文章/制度是偏差（单向广播不改变利益流向/自我指涉无受益者/署名仍是公司）；生成物=以基地名义、集体署名、交付给真实受益者的成果；第一个=课堂工作台（学员给自己造工具）；**校验标准**："这件事做完，谁的生活因为'实训基地'这四个字变好了？"
4. 系列引用链：动机→智慧→给予物，新篇写前先查 index 已有篇目接续引用；敏感信息（人名/金额/内部群细节）不入，机制与预测入

### 价值判据的应用偏差警示（2026-09-08 实证）

用户问"如何评价 insight 价值"后，五层判据已进 insight 仓 AGENTS.md 与 ROADMAP 双向校准机制（升格/预警/回滚三通道+验收/偏航两时机）——但**判据的薄弱环节是第五层（回声）**：多数存量 insight 证伪时限到期无人回头记账。改进方向（已建议未执行）：index.md 给每篇标注证伪时限，到期自动进入重审队列。写新 insight 时把证伪时限写具体（"两周内可证伪"而非"未来验证"），并预写证伪后的动作差异。

## 最小成本验证洞察（2026-09-12 实证）

核心一句：**验证成本 = 造证据的成本；要最小化就别造证据——用本来就会产生的证据。**

三种"本来就有"的证据（成本递增）：

1. **已经发生的**（零成本）——洞察多是已发生事情的规律化，先翻存量 journal / report / 案例库
2. **未来必然发生的**（近零成本）——**搭车验证**：挂到一件反正要做的工作上，只事先埋观测点
3. **为别的目的本来要做的**（成本已付）——真实使用，验证是副产品

最贵的是"为验证专门造一个场景"——这类先放一放。

三个降成本技巧：

- **预测改写成数得出来的形式**：对齐是瓶颈 → 每次人介入的原因分布；AI 产物质量差 → 同任务改稿轮次；流程破碎 → 一次任务跨手的系统个数。写不成的先改写，改不成的多半无法验证
- **优先找反例**：证伪只需一个反例，证实需一堆正例；找到一个反例就把洞察收窄成条件命题（"复杂系统构建中……"）
- **验证不了 = 该降级**：既无存量证据、又搭不上近期工作、也数不出指标 → 行动差≈0，当知识存着，别当依据用

**证据源选择**（用户："journal 和 profile 有丰富的证据可以验证，选择一个合适的"）：**一手自述（journal 里当事人当时的诊断）优于二手描述（profile 整理稿）**；profile 的全库词汇密度可作旁证——某个词反复出现即该处消耗最大（词频即成本）。

**验证记录的写法**：洞察文件末尾加「## 验证记录」节——日期 + 成本说明 + 判定表（断言 | 证据原文引句 | 判定）+ 旁证；**弱支持如实标注，不拔高**。验证的副产品常比结论更值钱：能收窄出**可测形式**（"反馈循环缺失" = 交付时有无判据），并修正原判断（"观察者最缺" → "只有雏形，已有「AI 建议 + 人确认」原则"）。

完整实证见 [references/insight-verification.md](references/insight-verification.md)。

### 边界被证据推翻时：当场改那一节（2026-09-12 实证）

用户用一句证据推翻你写进洞察的边界时，**当场改那一节并写明"原先判断不成立"**，不要静默保留、也不要只在对话里承认——洞察是公开仓库里的事实源，留着错边界会被下游引用。实证：`observer-pattern-seed.md` 初稿边界写"编程工序最难切细，切分是可分配的前提"，用户回"**可以切。看看 handbook 是怎么做的。**"→ 依 handbook 三件（件/场/程）与 code-implement 工作流改写边界节，开头明写"原先……的说法不成立"。

**判"能不能切"类边界先查 handbook，不凭感觉**：work 域 `docs/handbook/{piece/artifact.md, process/task.md, place/workspace.md}` = 切内容单元 / 切流动步骤 / 切工作边界三件，各自带「目标/步骤/验收」或「目标/流程/验收」；实例看工作区 `tasks/*.yaml`（步骤 + executor + 可机器判据）。切口随领域变——知识工作是**产物类别**，编程是**用例**；且切口往往同时就是洞察里要求的"中间表示"。

**code 域有自己的手册，切的是"这一类软件长什么样"**：`docs/handbook/{categories/, frameworks/, languages/}`。`categories/platform` 是平台契约，**按组件角色约定、不以项目为转移**（Provider=Go、Studio=Flutter、CLI=Rust）+ 统一约定（桶命名 `{产品线}-{用途}`、域名 `{产品}.cloud.example.com`、IaC 目录 `manifests/terraform/`、质量门禁 gofmt+go vet / dart format+flutter analyze / rustfmt+clippy「本地从严与 CI 一致」）。**两个手册各切一半**：work 手册切"怎么流动"（件/场/程），code 手册切"流动的东西长什么样"（类别/框架/语言）；编程的切口 = **组件角色 × 统一约定**，约定让产出可机器校验（门禁即判据）——这也是"确认权为何可下放"的答案：**先让对错变得可判，确认权才谈得上分配**。

**编程工作的切口实例（code-implement 工作流，四步）**：outline（逐动作/字段/判据列清单，来源是已实现的东西——不漏也不凭空多）→ doc（三部分文档，真实业务写成用例沉在使用指南，做过几件写几件）→ test（照用例设计测试、注释写出处；对账脚本做**双向对账**，文档用例号 ↔ 测试出处集合必须相等；**实现缺席时测试必须是红的**，挡恒绿空壳）→ code（写实现让测试变绿；要改从文档改起）。人的判断点只剩两处：文档定稿、代码验收。

**盘点式洞察写出处**：从现场盘出来的洞察（逐条带实例），**把每条要素的出处路径写进正文**（表格：要素｜现场形态｜出处）——这种"证据即内容"的篇目不受"证据压缩为一行"约束，因为它没有可回退的 journal 全文可指。

## 范围纪律（一词指令别扩写成结构方案）

用户给一词动作指令（"整理"）时**按最小范围执行，不要顺手新建结构**（工作区/材料分类/README/AGENTS 都算扩写）。实证：用户说"整理"，我回了一份含"建工作区 + 建材料分类 + 补 README"的四步方案 → 用户："不对。只把 Code 的 context 移动到 insight 整理。其他事情都不要做。"

配套三条：

- **跨域语境整理归语境所在的域**（code 域语境 → code 域 insight），不跨域搬运；目标域缺配套时只做被指定的那一步，缺什么单独提，别在同一轮顺手补齐
- 范围不清时**先问范围再动手**，问法给可选范围（A/B/C），别给整套结构方案
- **移动 = 内容迁出 + 原文件清空留占位**（日期文件保留 0 字节），提交信息写明迁出与去向
- **收尾提问要窄到具体文件**：改用"要我把它写进 `<具体文件>` 吗？只改那一个文件"代替"还要我做什么吗"——本会话实证：宽问（"要不要整理成 roadmap 条目 / 补齐 README"）拿到的是用户绕开提问另下指令，窄问一收到"yes"即可安全放行；一词指令（"整理"）则应先按最小范围执行，缺配套只单独提、不顺手补

## 提交规范

- Conventional Commits：`<域>: <描述>`（如 `qtclass: 集体给予物——...`）
- 同步 index.md（所属主题分节追加一行）
- 分层提交：insight 仓 → tech 主仓 data/insight 指针 → quanttide 根指针

## 篇目组织（insight 仓目录惯例）

- **主题目录 + 主文 `index.md` + 具名子篇同目录**：`<主题>/index.md` 是主文，该主题的切面写成同目录的具名文件——如 code 域 `code-agent/{index.md, observer.md, contract.md}`，与 tech 域 insight 仓的 qtclass/、qtcloud/ 同构；**别为子篇另建平级目录**（2026-09-12 用户纠正：先建成 `observer/index.md`，用户只回三个字 `code-agent/observer.md`——观察者本就是编程智能体的一个单元，属主题之下）
- 篇间**互链用同目录/相对路径**（`observer.md`、`../<主题>/index.md`），移动/改名篇目后随即修链（`git mv` 保历史）
- 归类优先沿用**组织已有词汇**命名目录与篇名（域的产品名或概念名），不新造代号
- 新建篇目前先读目录既有篇目接续引用，避免同一判断写两遍
- **洞察仓为空是常态、可以直接落第一篇**：不必先建 AGENTS/索引骨架（用户："其他事情都不要做"）——骨架随篇目生长
- **契约/结构类篇目**（如 `code-agent/contract.md`）的契约原型四件套、结构契约与依赖契约条款、借框架家法等明细，见 `quanttide-domain-design` 技能的「契约设计模式」节——写这类篇目前先读它，避免把已定型的契约判据重新推导一遍

## journal 整理分流的两阶段模型（2026-09-10 实证三轮纠正，work 域定稿）

journal（捕获与思考的现场记录）整理为**两阶段分离**，整理动作里彻底没有判断：

**阶段一（整理时）**：
1. 口述流水按主题分节润色——保判断性表述原样、去口语填充词
2. 移出的内容**一律先进材料库 `data/profile/<作者>/materials/<分类>/index.md`**（八分类：agent 智能体 / connect 沟通 / infra 基础设施 / work 知识工作 / org 组织管理 / write 写作 / meta 元工程 / course 课程；分类目录不存在就新建、里面放 index.md）——粗加工成「**标签**：内容」一节，一条一意、平实陈述，禁「不是…而是…」式表达
3. **归类 ≠ 归宿判断**：「进哪个材料分类」是整理动作的一部分（拿不准的单列交创始人裁决），「最终升级到 roadmap/handbook/insight」才是后置的认领动作——两者混为一谈就会重犯"整理时替未来做判断"的错
4. journal/语境的日期文件原文**删除**（不是摘要替代！），只留一份分流索引（各内容去了哪的清单带链接）；日期文件**留空占位（0 字节）**、目录保留

**流程已固化为工作流**（work 域 2026-09-11 观察，可平移到其他域）：`data/context/<工作区>/tasks/context-to-profile.yaml`——pull（拉语境、逐条读）→ classify（逐条认归属 + 拿不准单列）→ coarsen（粗加工进 `materials/<分类>/index.md`）→ move-out（已进材料的从日期文件删掉、留空）→ commit（材料仓与语境仓各自提交推送，再回工作区更新两个指针）。产物=报告 `artifacts/report/context-to-profile.md`（「条目清单」「条目→分类」「拿不准」「粗加工进材料」「迁出语境」五节），草稿区、由创始人点头后进 journal/report。工作区结构 `context/<工作区>/{tasks, artifacts/{report,journal}}`，工作区名随域（qtcloud-work / qtcloud-code…）。

**整理去向由用户指定，勿自作主张扩结构**：同一动作在不同域目的不同——work 域语境整理进材料库，code 域语境整理可**直出 insight**（2026-09-12 实证：code 域 09-12 整篇语境 → insight 一篇 `code-agent/index.md`）。用户说"整理"时按最小范围执行；目标域缺配套（工作区/材料分类/README）单独提，别在同一轮顺手补齐。

**阶段二（使用时，未来的独立场景）**：某段材料成熟被认领 → 从 default.md 升级进对应的家（roadmap 规格条目/handbook/insight）并从 default.md 删除。

**三轮纠正实录（每条都是违规律）**：
1. 把"规划类"直接写进 roadmap、只对材料节做摘要 → 用户："我让你整理到 profile/iGuo/default 备用，而不是直接整理到 roadmap"（整理时不做归宿判断）
2. 修正后仍留原文在 journal → 用户："journal 没清理，违反了工作规则"（原文删除是硬性的）
3. 正确形态：journal 文件 = 分流索引（"去了哪"清单），default.md = 全量材料（每条带来源链接回溯 journal 日期）

**惯例文本落点**：写进对应仓库 README（work 域 = data/journal/README.md"整理与移出的惯例"四则）。第 4 则措辞注意：写"没有明确归宿的才进 default.md"会留判断空间（出错根源），正确措辞是"**默认全部先移到 default.md，不论看起来是否像规格/规划；认领升级是后置动作**"。

**材料条目升级为 roadmap 时的模板**：定义/状态机位置/第一版范围/四阶段演进表挂接总路线推导轴（实证 roadmap/qtcloud-work/material.md）。

**与 context 驱动层的分工**（2026-09-10 同日定稿，含用户两次纠正）：journal 转型为"按时间线索传递上下文"（记录状态变化、指向生效中的 context），驱动规则归 context（data/context 仓库，handbook artifacts/context.md 规格）——工作物家族六件：语境（**驱动型·无时态**）+ 日志（状态线索）+ 档案/意图/洞察/路线图。验收对称判据："context 中没有一次性事件，journal 中没有驱动规则"。

**context 无时态（用户纠正："context没有时态。纠正一下"）——分界判据就在时态上**：语境不是对某个时点的陈述，而是当前生效的驱动规则，因此**不落"现在/未来 × 事件/语义"的时态格子**（六件里唯一无时态，别给它臆造类型轴），且**只保留最新版本**（规则型文档累积即自相矛盾；旧版删除，变更过程由 journal 时间线记录）。由此**insight ↔ context 的重复问题自然消解**：有预测的归 insight（带时态、可累积、到期走回声三处置），无时态的归 context（只留最新）——同一内容生命路径 = 洞察（当时的预测）→ 事实检验 → 稳定后升为 context 规则。用户"功能和洞察还稍微有点重复，一定要放最新的东西"即此判据的口语版。

**双向流动的显式表述（用户："新的context可以变成insight"）**：新形成的驱动认识**不直接写入 context**，先以 insight 形态存在（带预测与证伪条件），检验成立后才升格为语境规则——context 规格的转入因此是**两类来源**（① 洞察升格 ② 日志沉淀），验收多一条"**每条规则可溯源**：或来自洞察升格（有检验记录），或来自 journal 沉淀（有分流记录）"；insight 侧转出对应写"**两去哪**"（升格为语境 / 过期移除）。两份规格保持同一组措辞，否则两层又会含糊。
