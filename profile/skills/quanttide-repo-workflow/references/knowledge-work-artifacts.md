# 知识工作域（quanttide-work）文档体系速览

2026-09-10 定型。域仓 `domains/quanttide-work`（1 主 + 21 子模块）；有内容的只有三处：`docs/handbook`（v0.1.2，唯一的版本化发布）、`data/profile/iGuo`、`data/journal/iGuo`。

## 一、工作物矩阵（六件）

> **手册路径已变（2026-09-12 实测）**：手册重组为三件——`docs/handbook/piece/artifact.md`（产物规范）+ `process/task.md`（任务规范）+ `place/workspace.md`（工作区），手册自述\"**手册收规范：共性规则与做法；具体产物的案例见画廊**\"。旧的 `handbook/artifacts/`、`handbook/tasks/` 路径**已不存在**；六件工作物的逐件规格（目标/流程/验收）迁到 `docs/gallery/artifacts/*.md`（context/journal/profile/intention/insight/roadmap + specification/handbook/gallery 共九件），流程案例在 `gallery/workflows/`，工作区案例在 `gallery/workspaces/`。patch 前先 `find docs/handbook docs/gallery -type f` 看实际结构，别按记忆里的路径改。

| 工作物 | 时态轴 | 角色 | 流程 |
|---|---|---|---|
| **语境 context** | **无时态** | 驱动层 | 沉淀、修订、加载 |
| 日志 journal | 陈述型·现在×事件 | 状态线索 | 捕获、整理、分流、清空 |
| 档案 profile | 陈述型·现在×语义 | 沉淀层 | 转入、组织、转出 |
| 意图 intention | 陈述型·未来×自我 | 方向层 | 转入、组织、归档 |
| 洞察 insight | 陈述型·未来×语义 | 认知层 | 转入、组织、转出 |
| 路线图 roadmap | 陈述型·未来×事件 | 排序层 | 转入、组织、勾销 |

另有程序型三件：规格 specification、手册 handbook、案例 gallery。
任务 = 工作物之间的**流动关系**，不是工作物（规范见 `handbook/process/task.md`：按「目标/步骤/验收」三段编写，登记到画廊·流程；`gallery/workflows/` 现收两篇：从意图到路线图、从主体到领域）。

### 手册三件 = 切分方法（件 / 场 / 程）

手册收规范，按三种东西切：**件**（piece/artifact.md，切内容单元——角色唯一、三段式流动、单一去处、不留副本、可再找到、组织自主）／**场**（place/workspace.md，切工作边界——划界、域内流动、跨区流动、登记；\"工作区是一次工作的边界，区内工件与过程互相可见、区间彼此隔绝\"）／**程**（process/task.md，切流动步骤——目标/步骤/验收）。

判\"这类工作能不能切成流程\"时先查这三件：切法有规范可循，不是凭感觉切（实证：曾判断编程最难切细，被用户以\"可以切。看看 handbook 是怎么做的\"纠正，见第十一节）。

**「语境无时态」是硬判据**：语境不是对某个时点的陈述，而是当前生效的驱动规则——**不要给它臆造"现在/未来 × 事件/语义"的类型轴**（六件里只有它无时态）；推论：**只保留最新版本**（陈述型文档可按日期累积，规则型文档累积即自相矛盾；旧版删除，变更过程由 journal 时间线记录）。

## 二、journal ↔ context 的职责迁移

- **journal 原承担的"驱动"职能移交 context**：此前 journal 既是捕获入口又是事实源，AI/新会话要理解"现在怎么做"必须翻日志历史。
- **journal 转型为时间线索引**：记录每个时间点发生了什么状态变化、哪份 context 生效，本身不承载驱动规则。
- 验收对称判据：**context 中没有一次性事件，journal 中没有驱动规则**。

## 三、context ↔ insight 的分界（时态 + 检验状态）

- **insight**：带时态的规律认识（对未来的预测），可累积、可修正、可证伪
- **context**：无时态的驱动规则，只保留当前生效版本

**新的 context 先以 insight 形态存在**——刚形成的驱动认识不直接写入 context，先作为洞察存在（带预测与证伪条件）；实践检验成立后才升格为无时态的语境规则。被替换下来的旧 context 不保留，其历史意义由洞察层的检验记录承担（回声三处置：证实升格／证伪归因／问题消失归档）。
用户表述："功能和洞察还稍微有点重复，一定要放最新的东西" —— 即此判据。

## 四、journal 整理的「两阶段模型」（整理动作里没有判断）

**阶段一（整理时）**：口述流水分节润色 → 移出的内容**一律先进 `data/profile/<作者>/default.md` 作材料备用**（不做归宿判断）→ journal 原文**删除**，只留一份分流索引（各内容去了哪的清单带链接）。

**阶段二（使用时，未来独立场景）**：某段材料成熟被认领 → 从 default.md 升级进对应的家（roadmap /handbook /specification / insight）并从 default.md 删除。

惯例四则（写进 journal 仓的 AGENTS/README）：① 主题分节（保判断性表述、去口语填充词）；② 规格移出（原文删除留指引）；③ 摘要替代（仅用于整节移出的指引，不是留在 journal 的理由）；④ 兜底流向 default.md。

**措辞坑**：第 4 则写"没有明确归宿的才进 default.md"会留判断空间（出错根源）——正确措辞"**默认全部先移到 default.md，不论看起来是否像规格/规划；认领升级是后置动作**"。

## 五、材料（material）

`data/roadmap/qtcloud-work/material.md`（材料规格 = roadmap 条目模板：定义／状态机位置／第一版范围／四阶段演进表挂接总路线推导轴）。

- **定义**：已捕获、尚未被处理的输入；与备忘同源，区别是强调"**材料本身还没有被处理**"这个属性
- **第一版只实现材料**（遵守"第一个版本必须在没有大模型的情况下也有用"）；AI 访问边界限定第二大脑渠道
- **判断降级为整理**：判断显性化之后，AI 主要做信息整理（归入信息库/档案库）——这是引入大模型的前置条件

## 六、案例库（gallery）＝契约层的建设路径

**路径**：案例库（契约层）→ **把契约层配套的平台特性需求找出来** → 平台写出来上线 → 加强对知识工作过程之中契约的约束 → 提高工作效率与质量。

要点：案例库是**需求的探针不是产物**——通用平台最难的是"不知道要什么特性"；逐件写案例（每件标准产物的目标/流程/验收）是需求发现过程，契约写多细平台需求就有多具体（与"从代码出发逐渐导航"同源）。gallery 与 handbook 同构（目录同名、位置对应、可逐条对着读）；命名纪律：英文文件名定路径、中文标题定概念，**二者不互译**（`gallery.md` 不是 `case.md`、「案例」不是「画廊」）。

## 七、spec / contract 语汇

- **Specification** = 可接受行为的描述
- **Contract** = 交互双方义务与保证的、带责任分配的 specification
- 所有 contract 都可看作一种 spec，但不是所有 spec 都是 contract

## 八、默认工作目录（2026-09-11 定）

`data/context/iGuo/` 被标记为**默认工作目录**（context 仓 README「默认工作目录」节）：知识工作的默认起点——新会话、新成员、AI 系统开工先从这里读上下文，再按需进入其他资产。依据 = 领域第二大脑一般格式\"Context 是默认入口\"。

**稳态形态（实证观察）**：iGuo/ 下按日期一文件（`YYYY-MM-DD.md`），逐日捕获 → 内容移出到材料 → **日期文件留空占位**（不删文件，保留当日存在的事实）。\"日期文件留空占位\"是纯人工维持的环节——**它本身就是平台特性需求的种子**（自动按日建文件、移出后自动置空、移出记录自动索引）。

## 九、context ↔ insight 的流动细节（同日补）

- **context 转入两类来源**：① 洞察升格（新的驱动认识先在洞察层受检验——用户原话\"**新的 context 可以变成 insight**\"，即新规则不直接进 context）；② 日志沉淀（journal 整理出的稳定规则）
- **insight 转出\"两去哪\"**：升格为语境 / 过期移除（归档，不留原形式）
- **验收可溯源**：context 每条规则须能追溯（来自洞察升格=有检验记录，或来自 journal 沉淀=有分流记录）——这条把两层的对接变成可检查项

## 十、执行纪律（本域已实证的坑）

- 用户给出"降级 X 为 Y"类原则时，**该原则立即约束自己所有相关动作**（含刚执行过的流程）
- 用户含"是/定义/层"的短句可能是**路径/目的说明**而非定位判断——先照录原话，问清再落结构
- 整理流程**三轮纠正实录**：把"规划类"直接写进 roadmap ⇒ 整理时做了归宿判断（违规）；只对部分段落摘要替代、原文仍在 journal ⇒ 原文删除是硬性的
- 惯例文本落点按用户指定的文件（用户说"写到 journal 的 AGENTS"就写 AGENTS.md，README 只做入口）

## 十一、编程工作的切法：可以切，切口是用例（2026-09-12 实证）

曾有判断"编程的工序最难切细、切口不明"——**证伪**。用户一句话推翻："可以切。看看 handbook 是怎么做的。" 样本 = 工作区任务 `data/context/qtcloud-work/tasks/code-implement.yaml`（同一份也在 `data/profile/quanttide/workflows/code-implement.yaml`）：

**四步**（每步带 executor：agent/rule/human + 可机器判据）：

1. **outline**——逐动作、逐字段、逐判据列清单；来源 = 实验室已实现的东西，**不漏也不凭空多**
2. **doc**——重写三部分文档（user-guide / dev-guide / api-references）；**真实业务写成用例**沉在 user-guide 里，每条一个小节，做过几件写几件
3. **test**——照用例设计测试，每条测试上方注释写出处；写对账脚本做**双向对账**（文档用例号 ↔ 测试出处，两边集合必须相等）；对账结果与一次"红的记录"写进报告
4. **code**——写实现让测试变绿；**文档与测试这一轮不动，要改从文档改起**

**三个防虚假对齐机制**（可复用到别的域）：

- **双向对账**：文档与测试两边集合必须相等——机器可判，不靠人自觉
- **实现缺席必须红**：实现没写时测试必须是红的——挡"恒绿空壳"，证明测试真在测东西
- **文档先行、代码最后**：要改从文档改起，避免代码悄悄变成事实源

**人的判断点被压到两处**：文档定稿（内容取舍只能人拍）、代码验收（能不能上平台）；其余四步全是 AI 执行。且这两处**没绑定到具体个人**（只写"人拍"/"验收"）——对比发布/合并类工作流仍写"创始人确认"，说明**确认权可分配的形式在编程流里已经出现，缺的是把它从例外变成常规**。

**通用推论**：切口的选择随领域变——知识工作的切口是**产物类别**，编程的切口是**用例**；而用例同时就是观察者需要的中间表示（人可审查、可对账、可干预）。判断"某类工作能不能切成流程"时，先按手册三件（件/场/程）找切口，再落工作区 tasks yaml。
