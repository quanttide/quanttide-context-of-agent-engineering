# 文档写作纪律

## 目标

为量潮仓库（toolkit/应用/领域）写文档时，按读者问题顺序组织叙事、不用自造概念、一句话定位收到目的层。避免「开发者自嗨式架构罗列」与「发明的行话」。

## 流程

### 1. 叙事按读者问题顺序，不按架构展开顺序

读者的提问是递进的：这是什么/解什么问题 → 凭什么这么设计 → 怎么做到 → 还有什么也是这个思路 → 怎么用。按这个顺序组织，**不按代码结构顺序**（功能定位→三层管线→解析规则→提取器→语言包→共同结构 = 架构罗列，被改写）。

- 最有价值的东西放最显眼位置：核心论点（如「两个仓库同一套组织方式」）是论据不是附录，放在解法之后
- 一篇文章只干一件事：README（是什么）/ 设计文档（为什么）/ 参考（各模块干什么）三种文体不混在一篇里

### 2. 不自造口语化概念

「同构」「三层管线」「读懂层」这类发明词被否——改用平实描述（「同一套组织方式」「分三步」「语法解析/结构切分/语义提取」）。判断标准：**一个没背景的读者看到这个词能不能直接懂**；不能就是行话。术语用领域已有词（语法解析、结构切分），不造复合隐喻。

### 3. 一句话定位收到「目的」层，不是「手段」层

给目标读者的一句话介绍要连问几层「为什么」：
- 「把 Markdown 变成结构化数据」= 手段（被否「还不够本质」）
- 「人用目录和文件名表达结构，工具让 AI 照着约定理解」= 仍是手段（被否）
- 「人和 AI 在同一套知识结构上读写，还能在上面计算」= 目的（通过）

手段层描述的是「怎么做到」，目的层回答「为什么存在」。定位句写目的，方法写在正文里。

### 4. 通用逻辑归父级 docs/，特定逻辑归包内 doc/

多包仓库：`docs/index.md` 写所有包共用的逻辑（定位、机制、为什么这么设计）；`packages/<lang>/doc/index.md` 写该包特定的（目录结构、类职责、开发命令）。两处互引一行，内容不重复。

### 5. 写完切读者视角重读

逐段找理解困难：开头是否跳进术语？有没有「进→出」的具体例子？行话有没有解释？核心论点在第几节？发现问题按严重程度列出来再改。

### 6. 报告与复盘从意图层起写，细节只作支撑

维护报告 / 经验总结 / 复盘按四段写：**意图 → 结果 → 边界 → 下一步**。

- **意图**一句话说透「为什么做这件事」，下文所有处置都从这句话**推出来**（实证：「把 agent 的记忆拆开：授权进不可推翻的层，事实归仓库正本，工作记忆只留便条」→ 推出五类处置）。
- **结果**只写各范围做到哪一步；工程差错也照实写进去。
- **边界**写这轮真正想通的两三条（实证：「归档不是正本」「授权不受事实的规则管辖」）。
- **下一步**只写收尾动作与铺开方向。

**数字与清单是症状，不是内容。** 实证：第一稿把「39 条孤儿、159 个快照、16 个空目录」当内容铺开，5601 字节，被判「**细节太多，缺乏意图层的思考**」；重写成 2065 字节才过——那些数字只在**支撑某条判断**时才该出现。

## 反模式

| 反模式 | 案例 | 正确做法 |
|--------|------|---------|
| 架构顺序叙事 | 功能→管线→规则→提取器→包 | 读者问题顺序：问题→洞察→解法→验证→落地 |
| 自造概念 | 同构/三层管线/读懂层 | 同一套组织方式/分三步/语法解析 |
| 手段层定位 | 「让 AI 理解语义」「照着约定读」 | 目的层：「同一套结构上读写、计算」 |
| 文体混杂 | 一篇里 README+设计+参考 | 一篇一种文体 |
| 论点当附录 | 共同结构放最后 | 核心论据紧跟解法 |
| 术语堆砌无例子 | 全文抽象描述 | 先给「进→出」例子再讲道理 |
| 发现清单当内容 | 报告里铺开「39 条孤儿、159 个快照、16 个空目录」 | 意图先写；症状只在支撑某条判断时出现 |

## 验收

- [ ] 一句话定位是目的层（说「为什么存在」不说「怎么做到」）
- [ ] 报告/复盘类交付：意图段能推出下文其余部分；删掉纯数字罗列后主线不塌
- [ ] 全文无发明词（每个名词是领域已有词或直白描述）
- [ ] 叙事顺序 = 读者问题顺序
- [ ] 有具体例子（输入→输出）
- [ ] 读者视角重读过一遍，理解困难已修
